# 自造会话与自签令牌 — 从源码泄露到无密码身份伪造

> 沉淀自 HTB-Breadcrumbs（2026-10）。核心不是某个 payload，而是一条判据：**当应用不用框架默认的会话/令牌机制、改为自己生成时，认证就从"密码学问题"退化成"可预测字符串 + 可读文件"**。
> 配套阅读：`windows-webapp-foothold-to-local-admin.md`（同一靶机的服务端链路）。

## 1. 触发信号

命中任一即进入本笔记：

| 信号 | 常见位置 |
|---|---|
| 源码里**手动** `session_id($x)`（覆盖 PHP 默认随机 ID） | 登录成功分支 |
| 自写的会话/Cookie 生成函数（常叫 `makesession` / `genToken` / `makeCookie`） | `cookie.php`、`utils.php` |
| JWT / HMAC 密钥**硬编码**在源码里 | 认证控制器 |
| 同时存在**任意文件读/目录遍历**（哪怕只读） | 本笔记的全部威力来自这个组合 |
| Cookie 里同时有"框架会话"与"应用自签令牌"两套 | 两道门可用同一套手法同时伪造 |

**先决条件：先拿到源码。** 源码来源见 `playbooks/info-disclosure.md`、`playbooks/path-traversal.md`（LFI / 备份文件 / `.git` / 报错路径回显）。

## 2. 会话 ID 可预测：判断与枚举

### 2.1 判断

读 `session_id(...)` 实参函数的随机性来自哪里。典型反例：

```php
function makesession($username){
    $max = strlen($username) - 1;
    $seed = rand(0, $max);                       // ← 唯一的随机性
    $key = "s4lTy_stR1nG_".$username[$seed]."(!528./9890";
    $session_cookie = $username.md5($key);
    return $session_cookie;
}
```

| 生成式 | 候选空间 | 要点 |
|---|---|---|
| `md5($用户名)`（无盐） | 1 个 | 确定值，直接算 |
| `md5(固定盐 . $用户名)` | 1 个 | 确定值，直接算 |
| `$用户名 . md5(固定盐 . $用户名[rand(0, len-1)])` | `strlen($u)` 个 | ★ 随机只决定"取哪个字符"，全部可枚举 |
| `md5(固定盐 . $用户名[rand(0, len-1)])` | `strlen($u)` 个 | ★ 同上；**但不含用户名前缀 ⇒ 不同用户可能算出同一个 ID**，枚举时要意识到这点 |
| `uniqid()` / `microtime()` 派生 | 与时间窗相关 | 先按**时间戳型**测（回推服务器时间 + 窗口爆破） |
| `mt_rand()` / `rand()` 直接当 ID（不经哈希） | 取决于种子 | 属**种子可预测型**：**仅当应用自己调用了 `mt_srand()`/`srand()`（或运行在很旧的 PHP 上）种子才可推断**；否则现代 PHP 会自动用 CSPRNG 播种，此路不通。**动手前先确认版本与是否手工播种** |
| `random_bytes()` / `bin2hex(random_bytes())` | 不可枚举 | 放弃此路 |

**核心判据：随机数的取值空间是否只取决于"用户名长度"这类已知量。** 是 → 可枚举。

### 2.2 枚举

```bash
# 以 makesession() 为例：随机只决定"取用户名里的哪个字符"
for c in p a u l; do printf '%s' "s4lTy_stR1nG_${c}(!528./9890" | md5sum; done
```

**一次把全部候选算完再统一验证**，不要逐个试——命中率是 1/len，逐个试会把本可一次收敛的结论摊成多次请求。

### 2.3 验证：不要靠"登录成功与否"，直接去读会话存储

**PHP 的会话就是 `session.save_path` 下的普通文件**，文件名固定 `<前缀><会话ID>`（默认前缀 `sess_`）。所以：

- **有任意文件读** → 按候选文件名直接去读，**能读到内容的就是真实会话**
- **有任意文件写/上传** → 可自造会话文件（见 §5）

**⚠️ 判定纪律：只证明"会话 ID 可预测"是不充分的。** 只有当目标用户的会话文件**真实存在**时劫持才成立，否则你只是在猜一个不存在的会话。**必须读到文件内容（字段正确、非空）才算确认**，见 §6。

## 3. 令牌自签（以 JWT 为例）

### 3.1 从源码抄三件事，一个字都不要自己设计

| 要素 | 出处写法 | 说明 |
|---|---|---|
| 密钥 | `$secret_key = '...'` | HS 系列是**对称**的 → 能验就能签 |
| 算法 | `JWT::encode($payload, $key, 'HS256')` | 算法名要和源码一致 |
| payload 结构 | `array("data" => array("username" => $u))` | **照抄结构**，不要自创字段名 |

### 3.2 硬编码密钥的编码陷阱（实测踩坑）

密钥常长得像哈希（例如 64 个十六进制字符），**但它通常是当普通字符串用的**：

> **HMAC 的 key 是那 64 个 ASCII 字符，不是把它 hex 解码成 32 字节。**

用 `openssl` 时要先把**字符串**转成十六进制再喂 `hexkey:`：

```bash
b64u() { openssl base64 -A | tr '+/' '-_' | tr -d '='; }
H=$(printf '%s' '{"typ":"JWT","alg":"HS256"}' | b64u)
P=$(printf '%s' '{"data":{"username":"paul"}}' | b64u)
KEY='<源码里的密钥字符串>'
S=$(printf '%s' "$H.$P" | openssl dgst -sha256 -mac HMAC \
      -macopt "hexkey:$(printf '%s' "$KEY" | xxd -p -c 64)" -binary | b64u)
echo "$H.$P.$S"
```

**排错顺序**：签名验证失败时，**先怀疑 key 的编码，再怀疑 payload 结构**。库只会说"签名无效"，不会告诉你原因。

### 3.3 两个不必纠结的点

- **header 的键序不影响验签**：签名覆盖的是你实际发出的那串 base64 字节，`typ` 在 `alg` 前或后都行。
- **payload 里没有 `exp`/`nbf` 时令牌不过期**：源码没设就不要自己加。

## 4. 会话文件的位置

| 环境 | 默认 `session.save_path` | 线索 |
|---|---|---|
| Debian / Ubuntu（发行版 php 包） | `/var/lib/php/sessions/` | `php.ini` |
| XAMPP on Windows | `<xampp>\tmp\` | `php.ini`；**该目录同时也是 `upload_tmp_dir`** |
| 自建 / 容器 | 任意 | 读 `php.ini` 的 `session.save_path` |

**由此得到一条实用推论**：在 XAMPP 环境下，**一次失败的上传报错就能同时暴露 `upload_tmp_dir` 和 `session.save_path`**（PHP 的报错会把临时文件绝对路径打出来），不必再去翻 `php.ini`。

会话文件内容格式：

```
username|s:4:"paul";loggedIn|b:1;role|s:5:"Admin";
```

## 5. 写侧：会话投毒

若能写文件（上传 / 任意文件写 / 计划任务 / 同步目录），可直接投放自造会话：

```
文件名：sess_<makesession('目标用户')>
内容：  username|s:4:"<目标用户>";loggedIn|b:1;
```

**投毒点优先级**：任何"会被搬运/同步到会话目录"的中间目录 > 直接写会话目录。

**实例（HTB-Breadcrumbs）**：桌面上有一个 `.bat`，由"登录触发、每 5 分钟重复"的计划任务执行，内容是"把 `usefull_cookies\*` 复制到 `xampp\tmp\`"。这个本用于喂 cookie 的机制，反过来成了投毒通道。**遇到"定时搬运文件"的脚本，先想它能被当成写原语用。**

## 6. 判定纪律与常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 只验证会话 ID 可预测，不验证会话文件存在 | 劫持的是空气 | 先读到会话文件（非空 + 字段正确） |
| 只试一种候选 | 命中率 1/len | 全部候选一次算完，批量验证 |
| 把"数据库账号密码"当成"用户账号密码" | 登录失败后误判方案错误 | 区分 `db.php` 里的**库**凭据与**用户**凭据；用户密码常在别处（§7） |
| HMAC key 被 hex 解码 | 签名永远不对 | 见 §3.2 |
| 只伪造令牌、忘了会话（或反之） | 两道门只过一道 | **先读认证代码，把所有门列出来，再逐个伪造** |

## 7. 拿不到明文密码时的凭据猎取顺序

会话/令牌伪造能过应用认证，但**横向到 SSH/SMB 还需要真密码**。顺序建议：

1. 应用源码里的数据库凭据、硬编码串（如 `db.php`）
2. **web 根里"非字典命名"的目录** —— HTTP 爆破扫不到，必须用 shell 列文件系统（本项目就是这样找到一份含明文密码的 JSON）
3. 用户 profile 常规目录（Desktop / Downloads / Documents / OneDrive）
4. UWP / Store 应用数据 → `windows-webapp-foothold-to-local-admin.md` §4
5. 数据库表里的哈希 —— **先确认账号是否允许远程连接**，`1130` 是主机级拒绝，不是密码错

## 8. 防御视角（写报告时用）

- 会话 ID 必须来自 CSPRNG（`random_bytes()`），长度固定，**不得与用户名等可预测量存在任何函数关系**
- 不得手动 `session_id()` 覆盖框架默认值
- 签名密钥必须来自环境变量 / 密钥管理服务；且**避免使用"看起来像哈希的字符串"**（容易诱发 §3.2 的实现层错误）
- 会话存储目录不得位于 web 可访问路径，**也不得与上传临时目录共用**
- 任意文件读是这一切的放大器：任何文件读取接口都必须白名单化
