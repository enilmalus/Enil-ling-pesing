# 收尾自检方法论（报告初稿后必跑的 5 轮 × N 遍）

> 来源：2026-09 多目标授权渗透实战。**报告初稿完成后又跑了六轮收尾自检，累计补出 11 条发现——占第一批 21 条的 52%，其中包含唯一的严重项与 2/3 的高危项。**
> 结论先行：**初稿即交付 = 漏掉一半发现。** 本文件定义自检的 5 个固定轮次、每轮换什么切入点、以及实战踩过的坑。

---

## 0. 为什么必须做（本次实证）

| 阶段 | 产出 |
|---|---|
| 第一阶段（无账号，未登录视角） | **F1–F8 = 8 条**中低危，结论「安全基线中上」 |
| 第二阶段（取得低权账号） | 结论被**推翻**，补出 **F9（高）/ F10** |
| **六轮收尾自检** | **再补出 F11–F21 = 11 条**，含唯一的严重项（F15）与 2/3 的高危项（F13、F19），另有 1 处**结论性错误** + 1 处**整类漏测** |

**关键教训**：第一阶段「无 token 全部 401」的结论，**掩盖了「有低权 token 时全面放行」**。**没有账号 ≠ 没有越权面**，要显式声明覆盖限制。

## 1. 五轮固定框架

每一轮**换一个切入视角**。重复同一路径只会漏同样的东西。

| 轮次 | 视角 | 具体做法 | 本次补出 |
|---|---|---|---|
| **R1 类目对照** | WSTG 12 类逐项打钩 | 对每个高价值入口按 `methodology-standards-map.md` §2 对照表过一遍，标记「已触达 / 未触达 / 不适用（写理由）」 | 发现「**文件上传**」类目整类未触达 → F11；另一次自检发现 **WSTG-CRYP（弱加密）整类未触达** → 补测 TLS |
| **R2 端点清点** | 从**所有** JS bundle + 已登录响应提取端点，与已测清单比对 | 注意提取**前端不调用**的端点 | 补出 5 个未测端点（含文件上传接口本身） |
| **R3 绕过矩阵** | 编码 / 大小写 / 路径规范化 / 参数污染 / 方法变换 | 对已确认结论做反向验证 | 上传扩展名**大小写可绕**；`null` Origin 反射成立 |
| **R4 交叉回归** | 多站互测 + 跨站 token 互通 | 同源组内 A 的发现在 B 验证 | 确认 TLS 问题是**全组 CDN 共性**，非单站 |
| **R5 证据复核** | 逐条核对 HTTP 证据是否齐全 | 每条结论能否不看过程独立复现 | 补齐证据文件；**更正 1 处错误结论** |

## 2. 关键：第二轮之后要换「切入点」

> **编号说明**：下表用「**初稿后第 N 次自检**」编号（第一轮 = 初稿后跑的第一遍 5 轮框架）。**与具体项目报告里的编号可能不同**——报告常把初稿前那遍 5 轮自检也算作「第一轮」，导致整体后移一位。**引用时以「切入点」为准，不要只对编号。**

第一轮之后，如果还用同样的路径再跑一遍，收益趋近于零。**每轮必须换一个完全不同的切入点**：

| 轮次 | 切入点 | 为什么这个角度能挖到新的 |
|---|---|---|
| 第一轮 | 从 JS/响应推端点 + WSTG 类目对照 | 覆盖「前端调用过的」接口 |
| **第二轮** | **按框架已知高危组件清单反向枚举** | ★ 覆盖「**前端零调用**」的框架自带管理面 |
| **第三轮** | 鉴权绕过矩阵 + 日志反向枚举 + **写接口系统性普查** | ★ 覆盖「**读之外**」的写面 |
| **第四轮** | 文件读写面 + URL 参数面 | 覆盖「接口鉴权之外」的**参数本身能干什么** |
| **第五轮** | **对已获得的数据做二次挖掘** | ★ 覆盖「**已经拿到但没细看**」的数据 |
| **第六轮** | 登录方式操纵 + 认证后页面 + Cookie 属性 | 覆盖「**身份获取过程**」本身 |

## 3. 六条核心教训（按价值排序）

### 3.1 只跟「前端 JS → 端点」推，必漏框架自带的管理面 ★★★

**典型**：Quartz 定时任务接口 `/sys/quartzJob/*` —— **前端零调用**，只能靠「按框架高危组件清单反向枚举」发现。

**做法**：确认框架后，**主动列该框架的高危组件清单**（定时任务 / 数据源管理 / 报表引擎 / Actuator / 文件上传 / 字典动态查询 / 代码生成器 …），逐个探测。

### 3.2 「读接口可达」与「写接口可达」必须分别普查 ★★★

本次**第一、二轮只确认了读**，第三轮才系统性扫写接口，挖出**严重级**问题（可改任意用户密码 / 删账号 / 新增数据源）。

**做法**：读接口扫完后，**单独再扫一遍写接口**（`add`/`edit`/`delete`/`changePassword`/`upload` …），用 **GET 探 405** 零风险判定。

### 3.3 对报错接口不要直接判负，要尝试补全参数 ★★

**典型**：某接口缺参数时报 SQL 异常，**测试早期一直当「不可用」跳过**。直到某轮细看报错——**报错信息里直接打出了完整 SQL，参数名一目了然**。补上真实参数后，挖出「任意表/任意列读取」。

**做法**：对返回 500 / SQL 异常 / 参数校验错误的接口，**把报错原文读完**，从中反推参数名与数据类型，再补全重测。

### 3.4 已获得的数据本身也是攻击面 ★★

**典型**：拿到审计日志读权限后，第五轮对 2 万条日志做二次挖掘，既发现「日志未净化存储用户输入」，又挖出**厂商很可能不知情的历史攻击痕迹**（5 个账号、190+ 载荷、账号仍存活）。

**做法**：对任何能读到的大体量数据（日志 / 用户表 / 导出文件），**做关键词扫描与特征匹配**，不要只看前几行。

### 3.5 存在性探测用 GET 探 405 ★★

对写接口发 GET：**405 非 403 = 已穿过鉴权过滤器到达路由层**。零写入、零痕迹即可判定可达性。

> 具体用法与响应判读表见 `jeecg-boot.md` §2（该技巧在 JeecgBoot/Spring Security 系目标上验证过；其他框架需先确认其「方法不允许」与「无权限」的响应码是否可区分）。

### 3.6 重定向类参数要逐端点测 ★

**典型**：`/oauth/authorize` 的 `redirect_uri` **白名单有效**（4 种绕过全被拒），但**同族的 `/logout?redirect_uri=` 完全没设防** → 开放重定向。

**做法**：不能因 A 端点白名单有效就推定 B 端点也有效。**列出所有接受 `redirect_uri`/`returnUrl`/`url` 类参数的端点，逐个测。**

## 4. 自检自身的纪律

### 4.1 发现错误结论要**明确标注勘误**，不要悄悄改

本次自检中修正了 2 处自己的错误结论：

| 错误结论 | 实际 | 处理 |
|---|---|---|
| 「某站是 Tomcat 源站」 | 错误页页脚签名显示是**厂商自有服务**套用 Tomcat 风格 | 报告内加**勘误框**说明，而非静默修改 |
| 「查询串导致 400」 | 400 是**路径为根**导致，与查询串无关 | 负向结论表内标注「勘误」 |

**做法**：勘误写进报告，让甲方知道修正过程——这体现测试的可追溯性。

### 4.2 负向结论也要沉淀

「已测过且不成立」的项目要**列成负向结论表**，避免后续重复测试浪费预算。

### 4.3 自检本身也会出错

**自检脚本产生的「发现」必须先复核再当结论。** 实战中遇到的四类假阳性：

| 类型 | 例子 | 根因 |
|---|---|---|
| **宽松正则** | 用 `grep -qE 'Cipher is '` 判定弱套件，把 `Cipher is (NONE)`（握手失败）误判为「可协商」 | 匹配模式未排除失败态 |
| **脚本变量作用域** | 测试函数 `shift` 后 `$1` 为空，文件名没传进去，得出一批假结果 | 未验证脚本本身 |
| **检查范围过宽** | 扫描「新内容」时把整个文件的**原有条目**也扫进去，把原有的正确内容误报为问题 | 未限定扫描范围 |
| **关键词匹配过严** | 用「三字段坑」去 grep，而笔记写的是「三字段齐全」——语义相同却判为「缺失」 | 把关键词当语义 |

**做法**：**自检的结论同样要复核**——先判断「这是真问题，还是我的检查方式有问题」，再决定改不改内容。

### 4.4 结论有时效性

**WAF 规则可能在测试期间被实时收紧**。本次同一扩展名的上传结果在 10 分钟内变了三次（通过 → 部分拦截 → 全面拦截）。

**做法**：**每个结论都记录快照时间**（`date '+%H:%M:%S'`），并在报告中说明「该结论基于 X 时刻的观测」。

### 4.5 结论不得超出证据边界 ★★★

**这是自检里最难自查、也最容易翻车的一类**——因为错误不在「写得对不对」，而在「**证据支不支持**」。

本次实测踩到的两种形态：

| 形态 | 本次实例 | 问题 |
|---|---|---|
| **拿外部信息当目标事实** | 引用官方源码的 `getClass()` 实现，直接推断目标行为；但**目标实际行为与官方不同**（官方找不到类名会抛异常，目标却返回成功） | 官方源码只能作为**假设**，必须用目标实测行为验证 |
| **从现象推断结论** | 看到「上传文件以 `force-download` 下发」→ 写成「不构成 RCE」；但**上传目录的磁盘位置从未实测** | 现象只能支撑到现象本身；下游结论需要独立证据 |

**第三种形态：接口层确认 ≠ 数据面确认**

**实例**：某接口「未授权访问」已实测确认（无凭据返回 200 + JSON），但**所有测试号码都返回空数组**（系统中不存在企业绑定账号）→ **数据面无法验证**。

- ✅ 可写：「接口未授权已确认」
- ❌ 不可写：「该接口泄露企业信息」
- ✅ 正确做法：单列「未验证项」，说明**为什么验证不了**（缺什么前提），并给出甲方可补充的验证条件

**自查方法**：对每条结论问一句 ——「**如果甲方让我现场复现这条，我拿得出证据吗？**」
拿不出的，降级为「疑似 / 待验证」或补测。

## 5. 交付前：全量复现验证

初稿 + 自检完成后，**对全部 finding 逐条重新发一次真实请求**，确认仍然活跃。

### 5.1 必须区分的两种「失败」

| 报错 | 含义 | 处理 |
|---|---|---|
| `登录凭证已过期` | token 到期 | 重新取 token |
| **`当前账户已在其它设备登录!`** | **凭据被同账号新登录踢掉**（单会话策略） | **不是漏洞被修复**，重新取 token 即可 |

> **别把「token 失效」误判为「漏洞被修复」**——本次复验开始时 4 个 token 全部失效，一度以为目标已加固。

### 5.2 复现验证的产出

在报告中加一节「复现验证记录」，逐条列出：**验证方式 + 结果 + 快照时间**。这向甲方证明**所有结论都是当前有效、可复现的，不是历史快照**。

## 7. 一句话总结

> **初稿完成后至少再跑一轮 5 遍自检，且每轮必须换切入点。**
> 本次 **52% 的发现（11/21）、唯一的严重项、2/3 的高危项，都来自收尾自检**——**不跑自检的渗透报告，交付的是半成品。**
