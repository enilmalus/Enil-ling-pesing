# 多子域/多站点并行渗透编排（实战方法论）

> 来源：某保理平台多站点实测经验（员工端 bl / 供应商门户 dybl 同后端，两轮测试）+ 编排实践。
> 触发场景：用户给出 ≥2 个子域/站点要求测试。核心思想：**多目标 ≠ N 份独立单目标测试**——先聚类再分治，共享发现、矩阵汇报。

---

## 0. 流程总览

```
Phase 0 范围确认（逐站点）
   ↓
Step 1 被动聚类（同源判定，不发包/轻量）
   ↓
Step 2 按组分工：同源组=1 个测试单元，异源站=独立单元
   ↓
Step 3 并行执行（每单元独立跑单目标工作流 SKILL.md Phase 1-3）
   ↓
Step 4 交叉回归（同源组内互测：A 的发现在 B 验证）
   ↓
Step 5 矩阵汇总报告
```

## 1. 同源判定（Step 1，决定后面所有效率）

对每个站点轻量取证，按以下信号聚类：

| 信号 | 取法 | 同源含义 |
|---|---|---|
| DNS 解析 IP 交集 | dig A | 同源站/同机房 |
| TLS 证书 SAN | `openssl s_client` → x509 -ext subjectAltName | 通配符证书同持有者 |
| 前端 config-prod.js | 对比 `gateway_path`、`servers` 微服务列表、`web_path` | **最强信号：同一后端集群** |
| index.html 结构/ETag | HEAD 对比 | 同一套前端构建 |
| 错误响应特征 | 网关 401/404 body、traceId 格式 | 同网关中间件 |

**结论分三类**：
- **同后端组**（如 bl/dybl：config 里 `$servers` 完全一致）→ 按"1 个后端 + N 个前端入口"测，白名单/无鉴权接口全组共享
- **同前端不同配置**（如员工端/门户端用同一框架）→ 各自测，但框架级缺陷互查
- **完全异源** → 独立测，仅共享流程

## 2. 编排模式（Step 2-3）

### 2.1 子代理分工模板（harness Agent 工具）

```
主会话（编排者）职责：
- Phase 0 范围确认、目标分组
- 汇总各子代理 MUST 输出，维护全局发现清单
- 交叉回归的发起者（见 §3）
- 唯一有权写最终报告

每个子代理（1 个测试单元 = 1 个同源组或 1 个异源站）：
- 输入：目标 URL 清单 + 范围约束 + 已知共享信息（见下）
- 执行：SKILL.md Phase 1-3（侦察/枚举/漏洞探测）
- 输出：资产矩阵 + 发现清单（结构化：接口/证据/等级）+ 未决问题
- 禁止：写最终报告、横向到其他单元的目标
```

### 2.2 传给子代理的"已知共享信息"（关键省力点）

编排者聚类后，把一组内的共性下发，避免每个子代理重复发现：
- 微服务清单 + `$servers` 映射（一份就够）
- 已确认的白名单接口（组内所有站点直接回归，不用重新探测）
- 前端加密参数（AES key/IV/签名盐——同前端库则通用）
- 测试账号（组内 token 互通性待测，见 §3.2）

### 2.3 速率纪律（并行时最易失守）

- 每单元按单目标纪律限速，但**编排者要控全局并发**：同 IP 的多个站点共享目标方带宽/WAF 计数器
- 同机房站点（IP 交集）并发单元数减半；云 CDN 前置的（各站不同 CDN）可全并行
- 爆破/扫描类操作**不并行**——同源组内串行执行

## 3. 交叉回归（Step 4，同源组的核心增量价值）

### 3.1 漏洞回归矩阵

组内任一站点确认的漏洞，在其他站点的入口逐项复测：

| 发现类型 | 回归方法 |
|---|---|
| 网关白名单/无鉴权接口 | 同路径在其他站点域名下重放（大概率同配置）|
| 前端硬编码密钥 | 抓其他站点的 base 库对比（同库即同密钥）|
| 错误消息差分枚举 | 同接口族直接套用 |
| Source map 泄露 | 同构前端路径直接探测 |

### 3.2 跨站权限测试（最有价值的一环）

- A 站低权限 token → B 站网关：放行即**跨站垂直越权**（实战：供应商门户 token 在员工端网关直接放行管理接口）
- A 站账号体系与 B 站是否独立（登录接口报错差异判断；不共享则测"重置链"是否跨站生效——共用 cus 侧服务时会）
- JWT 结构对比：同 `opNo` claim 格式 = 同鉴权服务，密钥可能也同

### 3.3 回归发现单列

交叉回归产生的发现要在报告中标注"来源：组内回归"，与原生发现区分——它证明的是**缺陷的系统性**（配置模板问题），修复建议要提到"全组生效"。

## 4. 矩阵汇总报告（Step 5）

结构（在单目标模板上加两层）：

```markdown
## 执行摘要
- 站点分组结果：同源组 X（站点...）/ 异源站 Y（...）
- 风险统计（按组汇总）

## 漏洞 × 站点矩阵        ← 核心新增
| 漏洞 | 站点A | 站点B | 站点C | 备注 |
|------|-------|-------|-------|------|
| 任意用户密码重置 | ✅ | ✅(回归) | ❌ | 同后端配置 |

## 各站点漏洞详情          ← 单目标模板，按组组织
## 附录：分组依据（同源判定证据）
```

## 5. 实战要点（踩坑沉淀）

1. **聚类先行能省 50%+ 工作量**：dybl 的 9 个漏洞在 bl 全部同配置存在——如果不聚类，两套独立测试会重复劳动
2. **前端入口差异 ≠ 后端差异**：员工端/门户端界面完全不同，但 config 里 `$servers` 一致就是同一套微服务
3. **每站点仍要独立 Phase 0**：范围/授权可能不同（用户可能只授权部分子域）
4. **子代理输出必须结构化**（接口+证据+等级），否则汇总时主会话上下文爆炸——原始证据留文件系统，子代理只回传结论
5. **共享发现先回归再深挖**：组内新站点先跑已知漏洞回归（快），再开新攻击面（慢）——快速建立全组基线
6. **账号/token 集中管理**：编排者持有全部测试凭证并下发，子代理不各自注册（避免短信轰炸同一个手机号/触发风控）
