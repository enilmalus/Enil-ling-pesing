## 漏洞详情

每个 finding 一小节，格式固定：

### `[资产/URL] [漏洞类型] — 一句话描述`（标题 ≤80 字）

- **风险评级**：CVSS 3.1 vector `CVSS:3.1/AV:.../AC:.../...` + 严重度
- **漏洞描述**：成因与影响机制（2-4 句）
- **复现步骤**：
  1. 逐步可执行，附 curl 命令或 HTTP 包
  2. `[请求原文]` / `[响应原文]`
  3. 截图：`[文件名]`
- **影响分析**：业务影响 + 攻击者视角最坏结果；涉及利用行为的按 MITRE ATT&CK 战术归类（如 Credential Access / Lateral Movement），便于甲方对照检测覆盖（归类表见 `references/notes/methodology-standards-map.md` §3）
- **修复建议**：
  - 根因修复：`[代码/配置层面的修复]`
  - 缓解措施：`[WAF 规则/限制/监控]`
  - 优先级与工作量估计

## 输出纪律（提交前验证门）

每个 finding 写入漏洞详情前过一遍，任何一问不过 → 退回补证据或降级为待验证：

1. 复现步骤能独立重建吗（不看过程的人拿着报告能复现）？
2. 原始证据齐吗（HTTP 请求/响应原文、截图文件名）？
3. 评级是 CVSS 3.1 vector 推导的，不是直觉给的？
4. 影响分析含业务影响 + 攻击者最坏结果？
5. 修复建议按根因优先排序了？
6. 无证据观察已移入"附录·待验证项"，未混入漏洞详情？
